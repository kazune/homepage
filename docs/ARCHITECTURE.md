# Architecture

## 目的

このドキュメントは、個人ホームページの現時点の構成方針を定義する。

重要なのは、**今は小ネタの静的アプリを素早く増やすこと**であり、
大規模システムを先回りして作り込まないこと。

---

## 現在のスコープ

現在このリポジトリで扱うのは次の2つのみ。

1. サイト本体
2. 小さな静的アプリ

ここでいう小さな静的アプリとは、以下のようなものを指す。

- QRコード生成
- 文字数カウント
- テキスト整形
- JSON整形
- UUID生成
- 画像や文字列の単機能ツール

---

## 採用方針

### 1. 静的配信

このサイトは静的ファイルとして配信する。

- Apache2 は生成済みファイルを配信するだけ
- サーバーサイドアプリケーションは置かない
- DB は使わない

### 2. URL を固定する

アプリの公開URLは必ず次の形にする。

```text
/apps/<app-name>/
```

このルールは将来も維持する。

### 3. アプリ単位で独立させる

各アプリは、できるだけ他アプリに依存しない。
共通化は必要になるまで行わない。

### 4. 成果物は `dist/`

各アプリのビルド成果物はそのアプリ内の `dist/` に出力する。
公開時はそれらをルートの `dist/apps/<app-name>/` に配置する。

---

## ディレクトリ構成

```text
homepage/
  site/
  apps/
    <app-name>/
      src/
      dist/
      README.md
      app.json
  scripts/
  dist/
```

---

## app.json の役割

各アプリには `app.json` を置く。
これはアプリ一覧生成やメタ情報管理に使う。

例:

```json
{
  "name": "word-counter",
  "title": "Word Counter",
  "path": "/apps/word-counter/",
  "description": "文字数・単語数を数える小アプリ"
}
```

最低限必要な項目:

* `name`
* `title`
* `path`
* `description`

---

## デザイン方針

最初はシンプルさを優先する。

* 依存を増やしすぎない
* 単一HTML + CSS + JavaScript でもよい
* ビルド工程はできるだけ軽くする
* UI は過剰に凝らない
* まず動くものを優先する

---

## やらないこと

現時点では次をやらない。

* diary システムの実装
* CMS の導入
* 認証
* DB
* バックエンドAPI
* マイクロフロントエンド
* モノレポ管理ツールの複雑化
* 過度な共通コンポーネント化

---

## 将来の分離条件

次のような場合のみ別リポジトリ化を検討する。

* アプリ単体で継続的に更新する
* 依存やビルドが重い
* 専用のデータモデルが必要
* 単独デプロイしたい
* バックエンドが必要

ただし、それまではこのモノレポ内で管理する。

---

## 結論

このリポジトリは、しばらくの間
**小さな静的アプリを追加しやすいこと**
を最優先とする。

設計は拡張可能に保つが、拡張のために今の開発速度を落とさない。
