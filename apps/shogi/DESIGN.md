# 将棋アプリの設計方針

この文書は `.idea/shogi.md` を起点にした議論の合意をまとめる。
型の例は設計を説明するもので、未確定の項目は末尾に分ける。

## 基本方針

- 通常駒と多段移動駒を、同じシーケンス構造で扱う。
- 移動は `vector + range + pass + land` で表す。
- 候補表示は現在の段の着地点だけを対象とし、後続段の成立は先読みしない。
- 駒の定義は不変とし、位置の変化を `Transfer` として記録する。
- 特殊な規則をすべて汎用モデルへ押し込めず、必要に応じて専用処理を書く。
- ブラウザ内で完結する、小さく読みやすい TypeScript の実装にする。

## 移動規則の構造

```text
PieceType
 └─ SequenceRule[]
     └─ SequenceStage[]
         └─ MovementRule[]
             ├─ vector
             ├─ range
             ├─ pass
             └─ land
```

各配列の意味は次のとおり。

- `SequenceRule[]`：選択可能な移動シーケンス。
- `SequenceStage[]`：そのシーケンスで順番に実行する段。
- `MovementRule[]`：その段で選択可能な移動規則。

通常駒は段数が1のシーケンスを持つ。例えば飛車は、1段の中に4方向の移動規則を持つ。
多段移動駒は段数が2以上のシーケンスを持つ。

```ts
type SequenceRule = Readonly<{
  stages: readonly SequenceStage[];
}>;

type SequenceStage = Readonly<{
  movements: readonly MovementRule[];
}>;
```

### 途中終了

途中で手を終了できる場合は、その長さのシーケンスを別に定義する。
`canStop` などの属性は追加しない。定義の数が増えすぎる場合に再検討する。

例えば `[A]` と `[A, B]` を定義すると、Aまで実行して終了する手と、Bへ続ける手を表せる。
共通する段を進める間は、選択に適合するシーケンスを候補として保持する。
あるシーケンスが完了し、別のシーケンスが続行可能なら、終了と続行を選べる。

### 各段の評価

各段の `from` は直前の着地点とする。最初の段だけは、その手の開始位置を使う。
次段は、それまでの移動と捕獲を反映した仮盤面で評価する。
出発地点へ戻る移動も、この仕組みで扱う。

現在の段を選択した後、次段の候補が存在しなくても、事前には除外しない。
完了したシーケンスがなく、続行も不能になった段階で「合法に移動を終了できません」と表示する。
ユーザーは「待った」で選択前の状態へ戻って選び直せる。

## 1段の移動

### ベクトルと距離

`vector` は1回分の変位、`range` はその反復回数のうち着地できる範囲を表す。
距離は実際のマス数ではなく、ベクトルの適用回数。

- 歩：`[0, -1]` を1回。
- 桂馬：`[-1, -2]` または `[1, -2]` を1回。
- 飛車：上下左右の単位ベクトルを、盤外に出るまで反復。

ベクトルはプレイヤー基準で定義する。
評価時にプレイヤーに応じた回転変換を適用し、盤面座標の変位へ変換する。

上限なしの距離は `max: null` とする。探索は盤外に出たら終了する。
ゼロベクトルは繰り返し評価せず、1回だけ評価する。

### 通過と着地

ある着地点の評価では、その着地マスを `pass` の対象に含めない。

例えば距離3に着地するなら、距離1・2に `pass`、距離3に `land` を適用する。
同じマスでも、そこに着地する候補では `land`、さらに先へ進む候補では `pass` の対象となる。
距離1だけの移動には通過マスがないため、桂馬の移動で途中のマスは検査しない。

探索をまとめて行う場合は、各マスで着地可能性を評価し、その先へ進むための通過判定を行う。
通過できないマスでも着地できる場合があるため、通過失敗によってそのマスの着地候補を失わせない。
`range.min` 未満のマスも、先へ進むには通過判定が必要。

### 判定と効果

`pass` と `land` は許可・不許可と、捕獲などの効果を返す。
候補を表示するだけなら、捕獲対象の一覧を候補に保存する必要はない。
選択された移動の実行時に通過と着地を再評価し、効果を収集して適用する。

例えば格下を薙ぎ倒す駒がA、Bを通過して空マスCに着地する場合、実行時にはAとBの捕獲を適用する。
候補生成中に盤面を変更しない。

格による捕獲は、基本的には敵味方を区別しない。
区別が必要な規則では、`pass` や `land` の条件に所有者の判定を書く。

### 特殊規則

獅子のような多段移動も、段の進行自体は共通のシーケンス構造で扱う。
中将棋の獅子や自在天王など、各段の条件や効果に特殊な規則が必要な場合は専用処理を用意する。
すべてを表現するために基本モデルを複雑化しない。

## 駒と位置

駒の定義と現在位置を分離する。

```ts
type Piece = Readonly<{
  id: PieceId;
  type: PieceTypeId;
  owner: PlayerId;
}>;

type Location =
  | BoardLocation
  | HandLocation
  | VoidLocation;
```

- `BoardLocation`：盤上の位置。
- `HandLocation`：持ち駒の位置。
- `VoidLocation`：盤上・持ち駒から除外された状態。

`Piece` のID・駒種・所有者は生成後に変更しない。
現在位置は別に保持し、各駒は常にいずれかの `Location` に属する。

## 履歴とundo

駒の状態変化を位置間の移送として記録する。

```ts
type Transfer = Readonly<{
  pieceId: PieceId;
  from: Location;
  to: Location;
}>;

type Transaction = Readonly<{
  transfers: readonly Transfer[];
}>;
```

実行時は `transfers` の順に適用する。
undoでは逆順に処理し、各 `from` と `to` を交換する。
捕獲と移動など、まとめて戻す必要のある変更は同じトランザクションに入れる。

### 成りと持ち駒化

元の駒を除外し、別の定義を持つ新しい駒を生成する。
`Piece.type` や `Piece.owner` の変更履歴は持たない。

成りの例：

```text
元の歩：盤上 → Void
新しいと金：Void → 同じ盤上位置
```

捕獲して持ち駒にする例：

```text
捕獲された駒：盤上 → Void
捕獲側が所有する不成の新しい駒：Void → 持ち駒
```

新しい駒には新しいIDを割り当て、初期位置を `Void` として登録する。
生成した駒の定義はundo後も保持する。undoは新しい駒を `Void` へ戻し、元の駒を復帰させる。
redoを行う場合も、同じIDと定義を再利用できる。

### 進行状態の復元

`Transaction` は駒の位置変化を扱う。
「待った」では盤面に加え、手番、現在の段、候補として残っているシーケンス、手の完了状態を復元する必要がある。
これらは駒の移送履歴とは別に、復元できる形で保持する。
具体的な保存方法と「待った」の単位は未確定。

## 王族と決着

王の安全性は検査しない。王を捕獲してよく、詰みチェックも実装しない。

王や太子などの駒には王族を識別する属性を付与する。
決着はゲームごとの条件で判断する。例えば「自分の王族が0個になったら負け」とする。
王族の存在を数える際は、除外された駒の定義が残っていても、生存扱いにしない。

## 未確定の項目

- `rank` を `PieceType` に持たせる案の採用と、判定コンテキストから駒種を参照する方法。
- 成りの条件、任意・強制の区別、持ち駒や駒打ちを扱うゲームの範囲。
- 同じ着地点に異なる効果の移動規則がある場合の選択方法。
- 1段の途中で効果を収集する際、後続の規則が移動前と効果反映後のどちらの盤面を参照するか。
- ゼロベクトルでその場の行動を行う場合の、距離と自駒の扱い。
- 王族属性の具体的な型、決着を各段と手の終了のどちらで判定するか、双方が敗北条件を満たす場合の扱い。
- `BoardLocation`、`HandLocation`、`VoidLocation` の具体的な型。
- 「待った」で直前の段と手の開始のどちらへ戻すか、および進行状態の保存方法。
